02
Concepto

¿Qué es un remote?

Un remote es una versión de tu repo en otro servidor. GitHub y GitLab son remotos.

Tu PC
repo local
⇄ push / pull
GitHub / GitLab
remote "origin"
remotes
# Ver los remotes de tu repo
git remote -v
# origin  https://github.com/yo/proyecto.git (fetch)
# origin  https://github.com/yo/proyecto.git (push)

# Añadir un remote
git remote add origin git@github.com:yo/proyecto.git

# Cambiar la URL del remote
git remote set-url origin git@github.com:yo/proyecto.git

# Renombrar / borrar
git remote rename origin upstream
git remote remove origin
03
Decisión

HTTPS vs SSH

HTTPSSSH
ConfiguraciónNinguna, usa usuario/contraseñaGeneras una llave una vez
AutenticaciónToken o contraseñaLlave privada, sin escribirla
CortafuegosPuerto 443 (siempre abierto)Puerto 22 (a veces bloqueado)
SeguridadBuena con tokenMuy buena, no reusas credenciales
ComodidadPide credenciales a vecesTransparente tras configurar
Recomendación

SSH para tu día a día. HTTPS si el puerto 22 está bloqueado o en CI/CD con tokens efímeros.

04
Setup

Crear tus llaves SSH

Un par de llaves: la privada la guardas tú, la pública la pegas en GitHub/GitLab. Así te identificas sin contraseña.

generar llave ed25519
# Genera el par de llaves (algoritmo moderno recomendado)
ssh-keygen -t ed25519 -C "ana@ejemplo.com"
#   -t  tipo de llave (ed25519)
#   -C  comentario = tu email

# Preguntará:
#   Enter file:  Enter = ~/.ssh/id_ed25519
#   Passphrase:  contraseña opcional para la llave

# Si tu sistema no soporta ed25519:
ssh-keygen -t rsa -b 4096 -C "ana@ejemplo.com"
Dos archivos

id_ed25519 = PRIVADA (nunca la compartas). id_ed25519.pub = PÚBLICA (esa sí la subes a GitHub/GitLab).

05
Setup

El ssh-agent

El agent guarda tu llave en memoria para no pedirla cada vez. Si le pusiste passphrase, lo desbloqueas una vez por sesión.

ssh-agent
# Arranca el agente en background
eval "$(ssh-agent -s)"
# Agent pid 12345

# Añade tu llave privada al agente
ssh-add ~/.ssh/id_ed25519

# Ver las llaves cargadas
ssh-add -l
macOS

Para que el agente arranque solo al iniciar sesión, añade la llave al llavero: ssh-add --apple-use-keychain ~/.ssh/id_ed25519.

06
Setup

Registrar la llave pública

copiar la llave
# Copia el contenido de la llave PÚBLICA
cat ~/.ssh/id_ed25519.pub
# ssh-ed25519 AAAAC3Nza... ana@ejemplo.com

# macOS (al portapapeles)
pbcopy < ~/.ssh/id_ed25519.pub

# Linux (con xclip)
xclip -sel clip < ~/.ssh/id_ed25519.pub

# Windows (Git Bash)
clip < ~/.ssh/id_ed25519.pub

El fingerprint

La primera vez te pregunta si confías en el servidor. GitHub y GitLab publican sus fingerprints oficiales; comprueba que coincidan antes de aceptar.

08
Multi-cuenta

Varias llaves, varias cuentas

¿Cuenta personal y de trabajo? Usa ~/.ssh/config para que Git sepa qué llave usar.

~/.ssh/config
# Cuenta personal de GitHub
Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_personal
    IdentitiesOnly yes

# Cuenta de trabajo en GitHub
Host github-trabajo
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_trabajo
    IdentitiesOnly yes

# GitLab
Host gitlab.com
    HostName gitlab.com
    User git
    IdentityFile ~/.ssh/id_ed25519_gitlab
URL del remote

Para la cuenta de trabajo usa el alias como host: git remote set-url origin git@github-trabajo:empresa/repo.git

09
Sincronizar

fetch vs pull

fetch

Descarga los cambios del remoto, pero NO los mezcla con tu trabajo.

fetch
git fetch origin
# ahora compara lo que hay
git log HEAD..origin/main
# cuando decidas, haces merge
git merge origin/main

pull

fetch + merge en un solo paso. Rápido, pero menos control.

pull
git pull
# = git fetch + git merge

# mejor con rebase (historial limpio)
git pull --rebase
Hábito seguro

Antes de un pull en una rama con trabajo, usa git fetch para ver qué viene sin tocar tu rama.

10
Sincronizar

Subir con push

push
# Subir la rama actual al remoto (la primera vez)
git push -u origin feature/login
# -u = --set-upstream: enlaza local con remoto

# Las siguientes veces basta con
git push

# Subir todas las ramas
git push origin --all

# Subir los tags
git push origin --tags

# Borrar una rama remota
git push origin --delete feature/login
Rechazado

Si el remoto tiene commits que tú no tienes, el push se rechaza. Haz git pull --rebase primero y luego vuelve a push.

11
Rutina

Flujo de trabajo diario

feature/x
commit →
fetch
→ rebase →
push
→ PR
merge to main
rutina
# 1. Actualiza main y crea tu rama desde ahí
git switch main && git pull --rebase
git switch -c feature/login

# 2. Trabaja, haz commits
git commit -am "feat(auth): añadir login"

# 3. Antes de push, rebasea con main actualizado
git fetch origin
git rebase origin/main

# 4. Sube y abre el PR
git push -u origin feature/login
12
Conflictos remotos

Conflictos al sincronizar

resolver push rechazado
# El push falla: "non-fast-forward"
git push
# ! [rejected]  feature/login -> feature/login (fetch first)

# 1. Trae los cambios del remoto
git fetch origin

# 2. Replántate encima de lo que ya está allá
git rebase origin/feature/login

# 3. Resuelve conflictos si aparecen
#    edita archivos → git add → git rebase --continue

# 4. Vuelve a hacer push (forzar el rebase, no el merge)
git push --force-with-lease
--force vs --force-with-lease

Nunca uses --force a secas: puede pisar el trabajo de un compañero. --force-with-lease solo fuerza si nadie más subió commits.

13
Automatización

PRs/MRs sin salir del terminal

Con las CLIs oficiales abres PRs y MRs sin abrir el navegador.

🐙 GitHub — gh

gh pr create
gh pr create \
  --title "feat: login" \
  --body "Añade login con Google"
gh pr list
gh pr checkout 42
gh pr merge 42 --squash

🦊 GitLab — glab

glab mr create
glab mr create \
  --title "feat: login" \
  --description "Login con Google"
glab mr list
glab mr checkout 42
glab mr merge 42
CLIs

gh = GitHub CLI. glab = GitLab CLI. Las verás a fondo en sus módulos.

14
Open source

Fork and upstream

En proyectos ajenos no tienes permiso de push. Haces un fork (tu copia) y apuntas al original como upstream.

upstream
repo original
← pull --rebase
origin
tu fork
← push
tu local
fork flow
# Clona tu fork (origin apunta a tu copia)
git clone git@github.com:yo/proyecto.git
cd proyecto

# Añade el repo original como upstream
git remote add upstream git@github.com:original/proyecto.git

# Mantente al día con el original
git fetch upstream
git rebase upstream/main
15
Conveniencia

Ramas que siguen al remoto

tracking
# Crear rama local que sigue a una remota
git switch -c feature origin/feature
# o automático si el nombre coincide
git switch feature

# Enlazar una rama local ya existente
git branch -u origin/feature

# Ver qué rama sigue a cuál
git branch -vv

# Configurar pull para usar siempre rebase
git config --global pull.rebase true
Por defecto

Cuando clonas, tu rama main local ya sigue a origin/main. Por eso un simple git pull funciona sin argumentos.

16
Cultura

Revisión de código

📥

Pide revisión pronto

Un PR de 50 líneas se revisa bien. Uno de 500 se aprueba por cansancio. Commits pequeños = PRs pequeños.

💬

Comenta el código, no la persona

"Aquí podría fallar si X" no "escribiste mal esto".

🎯

Responde cada comentario

Aunque sea con un emoji. El autor sabe que lo leíste.

✅

Aprueba cuando el CI pasa

Verde en CI + revisión humana = merge. No esperes a la perfección.

Checklist

Checklist de colaboración

  • Llave SSH generada y registrada
  • ssh-agent cargado al iniciar sesión
  • pull configurado con rebase por defecto
  • main siempre limpio: trabajo en feature/
  • Commits pequeños con conventional commits
  • Antes de push: fetch + rebase origin/main
  • PRs con descripción y pasos para probar
  • Borro ramas tras cerrar el PR
  • Mantengo .gitignore al día
  • Configuré la CLI (gh o glab) para abrir PRs rápido
