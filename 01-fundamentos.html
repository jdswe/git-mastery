02
Concepto base

¿Qué es el control de versiones?

Un sistema que registra los cambios de un archivo (o un proyecto) a lo largo del tiempo. Así puedes volver a cualquier estado anterior.

📁

Sin control

proyecto_final_v2_REAL_final.docx → copias manuales, caos, cambios perdidos.

🌳

Con control

Un historial con cada cambio, quién lo hizo, cuándo y por qué. Vuelves a cualquier punto.

Idea clave

Git guarda fotografías (snapshots) de tu proyecto, no la diferencia línea por línea.

03
Motivación

¿Por qué Git y no otra cosa?

  • Distribuido: cada persona tiene el historial completo, sin depender de un servidor central.
  • Rápido: casi todo ocurre en local, sin red.
  • Ramificación barata: crear una rama cuesta casi nada.
  • Integridad: cada cambio tiene un hash (SHA-1) que lo identifica y protege.
  • Estándar: lo usa la industria entera.

04
Internals ligero

Cómo funciona por dentro

Git no guarda deltas (cambios). Guarda snapshots: una foto completa del proyecto en cada commit.

Commit 1
abc1234
→
Commit 2
def5678
→
Commit 3
ghi9012

Cada commit apunta al snapshot y al commit padre. Si un archivo no cambió, Git reusa la referencia anterior (ahorra espacio).

SHA-1

El hash abc1234 identifica el commit. Cambia un solo bit y el hash cambia completamente. Eso garantiza integridad.

07
Setup

Configuración inicial

Lo primero que haces en cualquier máquina: decirle a Git quién eres.

configuración global
# Tu nombre y email (queda en cada commit)
git config --global user.name "Ana López"
git config --global user.email "ana@ejemplo.com"

# El editor por defecto para mensajes de commit
git config --global core.editor "code --wait"

# Colores en la terminal
git config --global color.ui auto

# Rama por defecto al inicializar
git config --global init.defaultBranch main

# Ver toda tu configuración
git config --list
Tip

El flag --global aplica a todos tus repos. Sin él, solo al repo actual.

08
Práctica

Tu primer repositorio

Dos caminos: crear uno nuevo o traer uno que ya existe.

🌱 Crear nuevo

git init
# Crea una carpeta y conviértela en repo
mkdir mi-proyecto && cd mi-proyecto
git init
# Crea .git/  ← aquí vive el historial

⬇️ Clonar existente

git clone
# Trae un repo completo con todo su historial
git clone https://github.com/usuario/repo.git
# En una carpeta con otro nombre
git clone url mi-copia
Detrás de escena

git init crea la carpeta .git/. Esa carpeta es todo: el historial, las ramas, la configuración. Bórrala y el repo deja de ser un repo.

09
Flujo esencial

El flujo básico

Editas → preparas → confirmas. Estos tres comandos se repiten siempre.

add → commit
# 1. Crea o edita un archivo
echo "# Mi Proyecto" > README.md

# 2. Mira qué cambió
git status

# 3. Prepara el archivo para el commit
git add README.md
git add .          # prepara TODO (con cuidado)

# 4. Confirma con un mensaje claro
git commit -m "Añadir README inicial"

10
Diagnóstico

Ver el estado

git status es tu mejor amigo. Úsalo constantemente.

git status
git status
# On branch main
# Changes to be committed:
#   (use "git restore --staged ...") to unstage
#         new file:   README.md
#
# Changes not staged for commit:
#   (use "git add ..." to update)
#         modified:   app.js

# Versión compacta en una línea
git status -s
#  M app.js      (M = modified, no staged)
# A  README.md   (A = added, staged)
Lectura de letras

Columna 1 = estado en staging. Columna 2 = estado en working dir. ?? = archivo nuevo sin seguimiento.

12
Diagnóstico

Ver diferencias

git diff muestra qué cambió, línea por línea, antes de confirmar.

git diff
# Qué cambió pero NO preparaste aún
git diff

# Qué preparaste (staged) para el commit
git diff --staged

# Comparar dos commits
git diff a1b2c3d e4f5g6h

# Comparar dos ramas
git diff main feature

# Solo qué archivos cambiaron (sin el contenido)
git diff --stat
13
Corrección

Deshacer cambios

Tres niveles de deshacer, según el momento en que estás.

checkout · reset · restore
# Aún no preparaste el archivo (descarta cambios en working dir)
git restore app.js
# (antes: git checkout -- app.js)

# Ya preparaste pero quieres sacarlo del staging
git restore --staged app.js
# (antes: git reset HEAD app.js)

# Modificar el ÚLTIMO commit (mensaje o añadir archivos)
git commit --amend -m "Nuevo mensaje"

# Deshacer un commit creando uno nuevo (seguro, no toca historial)
git revert a1b2c3d
Cuidado

git reset --hard borra cambios para siempre. Úsalo solo cuando sabes que no los necesitas.

14
Higiene

Ignorar archivos con .gitignore

Algunos archivos nunca deben ir al repo: secretos, dependencias, compilados.

.gitignore
# Dependencias
node_modules/

# Compilados
*.o
*.class
dist/
build/

# Secrets — NUNCA los subas
.env
*.pem
config/secrets.yml

# SO
.DS_Store
Thumbs.db

# Logs
*.log

Plantillas listas

No escribas el tuyo desde cero. En gitignore.io o GitHub eliges tu lenguaje y te da el archivo completo.

Truco

¿Ya subiste un archivo y luego lo ignoraste? No basta con añadirlo al .gitignore. Debes sacarlo del seguimiento:
git rm --cached archivo

Manos a la obra

Ejercicio guiado

Crea tu primer repo de verdad. Abre una terminal y sigue los pasos.

ejercicio.md
# 1. Crea la carpeta del proyecto
mkdir recetas && cd recetas

# 2. Inicia el repositorio
git init

# 3. Crea tu primer archivo
echo "# Recetas de la Abuela" > recetas.md
echo "- Tacos al pastor" >> recetas.md

# 4. Prepara y confirma
git add recetas.md
git commit -m "Receta inicial: tacos al pastor"

# 5. Edita y vuelve a confirmar
echo "- Mole poblano" >> recetas.md
git commit -am "Añadir mole poblano"

# 6. Mira tu historial
git log --oneline
18
Trampas

Errores comunes

😬

commit sin mensaje claro

"arreglé cosas" no sirve. Describe el QUÉ y el POR QUÉ.

📦

commit gigante

10 cambios distintos en un commit. Separa: un commit = un cambio lógico.

🔑

subir secrets

API keys, contraseñas. Usa .gitignore desde el día uno.

🌲

trabajar siempre en main

Haz cambios en ramas, no directo en main. Lo verás en el módulo 2.

Estándar

Conventional Commits

Un formato estándar para que el historial sea legible y generable (changelogs, versiones).

formato
tipo(ámbito): descripción

# Ejemplos
feat(auth): añadir login con Google
fix(api): corregir crash al subir archivos vacíos
docs: actualizar guía de instalación
refactor(db): simplizar consultas de usuarios
test: añadir tests del módulo de pagos
chore: actualizar dependencias
BREAKING CHANGE: el endpoint /v1 ya no existe
TipoCuándo
featFunción nueva
fixCorrección de bug
docsSolo documentación
refactorCambio interno, sin nueva función
testAñadir o arreglar tests
