Teoría

Rebase interactivo

Reescribe el historial de tus commits locales antes de compartirlos. Aplasta, edita mensajes, reordena o elimina.

rebase -i
# Editar los últimos 4 commits
git rebase -i HEAD~4

# Se abre el editor con:
pick a1b2c3 feat: inicio login
pick d4e5f6 wip
pick g7h8i9 arreglé algo
pick j0k1l2 fix typo

# Cambias pick por:
#  r  → reword (solo edita el mensaje)
#  s  → squash  (aplasta en el anterior)
#  f  → fixup   (como squash pero descarta el mensaje)
#  d  → drop    (elimina el commit)
#  e  → edit    (pausa para modificar el commit)
03
Práctica

Rebase: limpiar tu rama paso a paso

práctica
# Tienes estos 4 commits sucios:
# a1b feat: inicio login
# d4e wip
# g7h arreglé algo
# j0k fix typo

git rebase -i HEAD~4
# Cambias a:
# pick a1b feat: inicio login
# fixup d4e wip
# fixup g7h arreglé algo
# fixup j0k fix typo

# Resultado: un único commit limpio
# a1b feat(auth): inicio login

# Si ya subiste la rama, fuerza con seguridad:
git push --force-with-lease
Regla

Solo rebasea commits que nadie más ha visto. Nunca rebasees main ni ramas compartidas.

04
Teoría + práctica

El reflog — tu red de seguridad

Git registra cada movimiento de HEAD. Aunque borres una rama o hagas reset, reflog te deja volver.

reflog
# Ver el reflog completo
git reflog
# a1b2c3 HEAD@{0}: commit: feat: login
# d4e5f6 HEAD@{1}: rebase: finish
# g7h8i9 HEAD@{2}: switch: moving from main

# Accidente: hiciste reset --hard y perdiste commits
git reflog              # busca el hash que necesitas
git switch -c recovery HEAD@{3}  # crea rama desde ese punto

# Ver reflog de una rama específica
git reflog feature/login
30 días

Las entradas del reflog viven 30 días (90 para las inalcanzables). Después las borra el garbage collection.

05
Teoría + práctica

Encontrar bugs con git bisect

bisect hace una búsqueda binaria en el historial para encontrar qué commit introdujo un bug.

bisect
# 1. Inicia bisect
git bisect start

# 2. Marca el commit actual como "malo" (bug presente)
git bisect bad

# 3. Marca el último commit que sí funcionaba como "bueno"
git bisect good v1.0.0   # o un hash

# Git te lleva a la mitad del historial
# Prueba si el bug está:
git bisect good    # o
git bisect bad

# Repite hasta que Git te diga el commit culpable
# Vuelve al estado normal
git bisect reset
06
Práctica

bisect automatizado

Pasa un script que retorna 0 (bueno) o 1 (malo) y bisect corre solo.

bisect run
# Script de prueba: test.sh
#!/bin/bash
npm test 2>&1 | grep -q "PASS"

# Bisect automático: prueba ~log2(N) commits
git bisect start
git bisect bad HEAD
git bisect good v1.0.0
git bisect run bash test.sh

# → Encuentra el commit culpable en segundos
git bisect reset
Tip

Para 1000 commits, bisect solo necesita ~10 pruebas. Mucho más rápido que revisar uno a uno.

Git Hooks

Scripts que Git ejecuta automáticamente en eventos: antes de commit, después de push, antes de merge…

HookCuándo correUso típico
pre-commitAntes del commitLint, format, tests
commit-msgValidar el mensajeConventional commits
pre-pushAntes de pushCorrer suite de tests
post-mergeDespués de mergenpm install si cambió package.json
pre-rebaseAntes de rebaseProteger ramas compartidas
08
Práctica

Hooks en práctica

.git/hooks/pre-commit
#!/bin/sh
# Corre lint antes de cada commit
npm run lint --silent
if [ $? -ne 0 ]; then
  echo "❌ Lint falló. Corrígelo antes de confirmar."
  exit 1
fi
con Husky (hooks compartidos en equipo)
# Instala Husky (hooks se comparten via package.json)
npm install --save-dev husky
npx husky init

# .husky/pre-commit
npm run lint && npm test
¿Por qué Husky?

Los hooks en .git/ son solo locales. Husky los guarda en .husky/ que SÍ se commitea y comparte con el equipo.

Teoría

Git submodules

Un repo dentro de otro. El padre almacena un puntero (hash de commit) hacia el hijo.

submodule
# Añadir un submodule
git submodule add git@github.com:org/libreria.git libs/libreria

# Clonar un repo con submodules
git clone --recurse-submodules git@github.com:org/app.git

# Si ya clonaste sin --recurse
git submodule update --init --recursive

# Actualizar todos los submodules al último commit de su rama
git submodule update --remote --merge

# Ver el estado de cada submodule
git submodule status
Complejidad

Los submodules son potentes pero complejos. Para la mayoría de equipos, un gestor de paquetes (npm, pip) es más simple. Usa submodules solo cuando necesitas el repo completo con su historial.

10
Teoría + práctica

Git worktrees

Abre múltiples ramas al mismo tiempo en carpetas distintas — del mismo repo, sin stash.

worktree
# Añadir un worktree para una rama
git worktree add ../hotfix hotfix/crash

# Ahora tienes dos carpetas con el mismo repo
# ~/proyecto        → main
# ~/hotfix          → hotfix/crash

# Ver los worktrees activos
git worktree list

# Eliminar un worktree cuando terminas
git worktree remove ../hotfix
Cuándo usar

Perfecto para un hotfix rápido mientras estás en medio de otra feature. Sin stash, sin cambiar de rama. Dos carpetas, dos ramas, el mismo .git.

11
Utilidad

Exportar sin .git/

archive
# Exportar el proyecto como ZIP sin la carpeta .git/
git archive --format=zip HEAD > proyecto.zip

# Solo una subcarpeta
git archive --format=tar HEAD:src > src.tar

# Un commit o tag específico
git archive --format=zip v1.0.0 > v1.0.0.zip
12
Utilidad

Notas en commits

Añade metadatos a un commit sin reescribir su hash. Se usa en herramientas automáticas y flujos de revisión.

notes
# Añadir una nota a un commit
git notes add -m "Revisado por Ana · jira=PROJ-42" a1b2c3d

# Ver las notas de un commit
git notes show a1b2c3d

# Ver el log con notas
git log --show-notes=*
13
Herramientas potentes

Reescribir historial con seguridad

git-filter-repo
# Instala git-filter-repo (reemplaza filter-branch, más rápido)
pip install git-filter-repo   # o brew install git-filter-repo

# Eliminar un archivo de TODO el historial
git filter-repo --path secreto.env --invert-paths

# Cambiar el email del autor en todo el historial
git filter-repo --email-callback \
  "return email if email != b'viejo@mail.com' else b'nuevo@mail.com'"
Destructivo

filter-repo reescribe todos los commits, cambiando los hashes. Todos deben reclonar. Coordínate con el equipo.

14
Repos grandes

Sparse checkout

Solo abre las carpetas que necesitas. Útil para monorepos con cientos de paquetes.

sparse-checkout
# Clona sin los archivos de trabajo
git clone --filter=blob:none --sparse git@github.com:org/monorepo.git
cd monorepo

# Inicializa sparse en modo cone (rápido)
git sparse-checkout set --cone

# Añade solo las carpetas que necesitas
git sparse-checkout add packages/api packages/shared

# Ver qué está incluido
git sparse-checkout list
15
Control fino

.gitattributes

.gitattributes
# Normaliza line endings (Windows ↔ Unix)
*         text=auto
*.sh      text eol=lf
*.bat     text eol=crlf

# Archivos binarios: no hacer diff ni merge
*.png     binary
*.pdf     binary

# Usar un diff driver personalizado
*.docx    diff=word

# Excluir archivos de git archive (exportar)
.github/  export-ignore
tests/    export-ignore
