Teoría

Git internals — objetos

Todo en .git es un objeto direccionado por su hash SHA-1. Tres tipos principales:

📄

blob

El contenido de un archivo (sin nombre, sin ruta).

🌳

tree

Una carpeta: lista blobs y sub-trees con sus nombres.

🔗

commit

Apunta a una tree + padre + autor/mensaje.

🏷️

tag

Un tag anotado también es un objeto.

Idea clave

Un commit apunta a una tree (el snapshot); la tree apunta a blobs (los archivos). Cambia un byte y todos los hashes de la cadena cambian.

03
Práctica

Mira dentro con cat-file

comandos plumbing
# Ver el tipo de un objeto por su hash
git cat-file -t a1b2c3d
# commit

# Ver el contenido (legible)
git cat-file -p a1b2c3d
# tree 9f8e7d...  author: Ana ...  parent: ...

# Inspeccionar la tree de ese commit
git ls-tree a1b2c3d
# 100644 blob 3a2b1c...  README.md

# Crear un blob a mano desde un archivo
git hash-object -w app.js
# → devuelve el hash del nuevo blob

# Contar objetos y su tamaño
git count-objects -vH
Por qué importa

Saber plumbing te permite recuperar datos, escribir hooks personalizados y depurar lo imposible.

05
Teoría + práctica

Desarrollo trunk-based

Todos commitean a main (o ramas muy cortas < 2 días). Las features incompletas se esconden tras feature flags.

patrón feature flag
# código/main.go
if config.FeatureEnabled("new_checkout") {
    return newCheckout()
}
return oldCheckout()

# La feature vive en main pero apagada; la activas cuando esté lista
Por qué

Ramas cortas = menos conflictos, integración rápida, PRs más pequeños.

Teoría + práctica

Monorepos en Git

Un repo, muchos proyectos. Git lo maneja, pero usas herramientas para mantenerlo rápido.

kit de monorepo
# Solo bajar las carpetas que necesitas (sin clonar todo)
git clone --filter=blob:none --sparse git@github.com:org/mono.git
git sparse-checkout set apps/web apps/api

# Herramientas que escalan el monorepo:
#  - pnpm workspaces / npm workspaces  (JS)
#  - Nx / Turborepo                   (build cache, affected)
#  - Bazel                            (multi-lenguaje)

# "Solo construye lo que cambió" (Turborepo)
npx turbo run build --filter=...@org/ui@latest
Práctica

Sparse checkout + un cache de build (Nx/Turbo) = monorepo tan rápido como un repo pequeño.

Teoría + práctica

Commits firmados — GPG

Un commit firmado prueba que vino de verdad de ti. GitHub/GitLab muestran el sello 'Verified'.

setup GPG
# 1. Genera una llave GPG
gpg --full-generate-key
#    → tipo RSA, 4096, tu email (el mismo de GitHub)

# 2. Lista tus llaves y copia el ID
gpg --list-secret-keys --keyid-format=long

# 3. Dile a Git que firme con esa llave
git config --global user.signingkey ABCD1234
git config --global commit.gpgsign true

# 4. Firma un commit
git commit -S -m "feat: login"

# 5. Exporta la llave pública y súbelo a GitHub
gpg --armor --export ABCD1234 | pbcopy
08
Práctica

Commits firmados — SSH

Nuevo y simple: firma con la misma llave SSH que ya usas para push. Sin configurar GPG.

firma SSH
# 1. Dile a Git que firme con SSH
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true

# 2. Sube la MISMA llave pública a GitHub como "Signing Key"
#    Settings → SSH and GPG keys → New SSH key → tipo: Signing Key

# 3. Firma
git commit -S -m "feat: login"

# 4. Verifica localmente
git verify-commit HEAD
Tip

Firma SSH = una llave para auth y firma. Menos cosas que gestionar que GPG.

Seguridad · teoría

.env & secrets — regla de oro

Los secretos (API keys, contraseñas de DB, tokens) NUNCA van al repo. Una vez pusheados, considéralos filtrados.

Si ya subiste un secreto

1) Rótalo ya (genera uno nuevo). 2) Bórralo del historial. 3) No basta con borrar el archivo — los commits viejos todavía lo tienen.

Regla de oro

Los valores reales viven fuera del repo (env vars, un vault, variables de CI/CD). El repo solo guarda una plantilla con valores falsos.

# 3. La librería los lee en runtime (dotenv, os.Getenv, etc.)
11
Seguridad · práctica

git-secrets — bloquea secretos antes del commit

git-secrets
# Instala (macOS)
brew install git-secrets
# Linux: clona y make install
git clone https://github.com/awslabs/git-secrets && cd git-secrets && make install

# Activa en un repo (instala un hook pre-commit que escanea)
git secrets --install
# Añade patrones (AWS por defecto + los tuyos)
git secrets --register-aws
git secrets --add 'password\s*=\s*.*'

# Escanea todo el historial en busca de secretos ya subidos
git secrets --scan-history
Más herramientas

GitHub secret scanning + GitLab secret detection detectan fugas en el servidor. gitleaks y trufflehog escanean local y en CI.

12
Seguridad · recuperación

Borrar un secreto filtrado del historial

git filter-repo
# 1. PRIMERO rota el secreto (genera uno nuevo). El viejo ya está comprometido.
# 2. Borra el archivo de TODO el historial
git filter-repo --path .env --invert-paths

# 3. O borra solo la línea con el secreto
git filter-repo --replace-text expressions.txt
#   expressions.txt:  VIEJO_SECRETO==>***REMOVIDO***

# 4. Fuerza el push (todos los hashes cambiaron)
git push --force-with-lease --all

# 5. Avisa al equipo: todos deben re-clonar
El orden importa

Rota primero, luego limpia. Si limpias primero, el secreto sigue válido y los atacantes pueden tenerlo ya.

13
Auditoría

Auditoría y forense

encontrar cualquier cosa
# ¿Quién cambió cada línea?
git blame app.js -L 10,30

# ¿Cuándo se añadió/borró una cadena? (-S busca additions)
git log -S "API_KEY=abc123" --oneline

# Commits cuyo mensaje coincide con un patrón
git log --grep "CVE" --grep "security" --all-match

# Todos los commits de una persona
git log --author="Ana" --since="2 weeks ago"

# Ver qué hizo cada persona (reporte corto)
git shortlog -sne

# ¿Qué referencias apuntan a un commit? (para auditoría de merges)
git branch --contains a1b2c3d

Performance

Salud del repo

mantenimiento
# Limpia y compacta objetos (repo más rápido y pequeño)
git gc --prune=now
git gc --aggressive

# Verifica la integridad del repo
git fsck --full

# Pre-empaqueta objetos compartidos (clone más rápido)
git repack -a -d --depth=250 --window=250

# ¿Qué rama local ya se mergeó? (para limpiar)
git branch --merged main

# Evita que archivos enormes ensucien el repo
git config --global core.bigFileThreshold 50m

Archivos grandes

Git LFS — archivos grandes

Git guarda un puntero diminuto en el repo; el archivo grande real (video, modelo, binario) vive en el servidor LFS.

setup LFS
# Instala (una vez por máquina)
brew install git-lfs   # o: apt install git-lfs
git lfs install

# Dile qué archivos van por LFS
git lfs track "*.psd"
git lfs track "videos/*.mp4"

# ¡commitea el .gitattributes! (define el tracking)
git add .gitattributes

# Ahora add/commit funciona normal, pero los grandes van al LFS
git add diseño.psd && git commit -m "Añadir diseño"

# Ver qué rastrea LFS
git lfs ls-files
