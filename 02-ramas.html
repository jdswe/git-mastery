02
Concepto

¿Qué es una rama?

Una rama es un puntero ligero a un commit. Crear una rama no copia nada: solo crea una referencia nueva.

A --- B --- C ← main \ D --- E ← feature/login
⚡

Instantáneo

Crear o borrar una rama tarda microsegundos. No hay copia de archivos.

🛡️

Aislado

Los cambios en tu rama no afectan a main ni a otras hasta que haces merge.

🔀

Paralelo

El equipo trabaja en 10 ramas a la vez sin pisarse los pies.

03
Cómo lo ve GitHub/GitLab

El grafo del repositorio

Esto es justo lo que muestran GitHub y GitLab en Repository → Graph. main al centro; cada rama feature se bifurca, añade su commit y vuelve a merge.

04
Teoría

Cómo leer el grafo

  • Cada línea de color es una rama. Verde = main.
  • Los puntos son commits. Los más nuevos arriba.
  • Una línea que sale de main = se creó una rama (se bifurcó).
  • Una línea que vuelve a main = ocurrió un merge.
  • Los avatares y badges muestran quién y en qué rama.
Real

Es la misma vista que git log --oneline --graph --all — solo más bonita.

05
Comandos

Crear y cambiar ramas

branch · checkout · switch
# Ver todas las ramas locales
git branch

# Ver ramas locales Y remotas
git branch -a

# Crear nueva rama
git branch feature/login

# Cambiar a esa rama
git switch feature/login
# (antes: git checkout feature/login)

# Crear Y cambiar en un solo paso
git switch -c feature/login
# (antes: git checkout -b feature/login)

# Volver a la rama anterior
git switch -
Moderno

git switch y git restore son los nuevos comandos desde Git 2.23. Más claros que el viejo git checkout.

07
Merge

Merge fast-forward

Cuando main no tiene commits nuevos desde que se bifurcó la rama, Git solo mueve el puntero.

Antes
→git merge feature
Después
merge fast-forward
git switch main
git merge feature/login
# Fast-forward — no crea commit de merge
¿Cuándo?

Solo si no hubo divergencia. Es el merge más limpio porque no añade ruido al historial.

08
Merge

3-way merge

Cuando main también tuvo commits nuevos, Git crea un commit de fusión con dos padres.

Antes
→git merge feature
Después
merge con historial
git switch main
git merge feature/login
# Abre el editor para el mensaje del commit M

# Forzar el commit de merge (nunca fast-forward)
git merge --no-ff feature/login
09
Conflictos

Resolver conflictos

Un conflicto ocurre cuando dos ramas editaron la misma línea de forma distinta. Git lo marca así:

archivo en conflicto
<<<<<<< HEAD
color: rojo;          ← lo que tienes tú (main)
=======
color: azul;          ← lo que trae la rama
>>>>>>> feature/theme
pasos para resolver
# 1. Git dice qué archivos tienen conflicto
git status

# 2. Abre los archivos, decide cuál versión queda (o mezcla)
#    Borra las líneas  <<<, === y >>>  cuando termines

# 3. Prepara los archivos resueltos
git add archivo.css

# 4. Cierra el merge
git commit

# Si quieres cancelar y volver atrás
git merge --abort
10
Reescritura

Rebase

Rebase "replanta" tus commits sobre la punta de otra rama. Historial lineal, sin commit de merge.

Antes
→git rebase main
Después
rebase básico
git switch feature
git rebase main
# Resuelve conflictos si los hay, luego:
git rebase --continue
Regla de oro

Nunca hagas rebase de commits que ya están en una rama compartida (main, develop). Solo rebasea tu rama local.

11
Comparación

Merge vs Rebase

MergeRebase
HistorialRamificado, con commit MLineal, sin commits extra
TrazabilidadMuestra cuándo se unió la ramaNo es claro cuándo fue
ConflictosUna vez, al hacer el mergeUna vez por cada commit
Commits originalesIntactos, mismo hashNuevos hashes (D → D')
Uso recomendadoPRs, integración a mainLimpiar tu rama antes del PR
Práctica habitual

Usa rebase para limpiar tu rama local antes de abrir el PR, y merge para integrar el PR en main.

12
Precisión

Cherry-pick

Tomar un commit específico de una rama y aplicarlo en otra, sin traerte toda la rama.

feature → main
→git cherry-pick C
cherry-pick
# Busca el hash del commit que quieres
git log --oneline feature

# Aplícalo en la rama actual
git switch main
git cherry-pick abc1234

# Varios commits seguidos
git cherry-pick abc1234..def5678
Cuándo

Un hotfix que necesitas en main y en release/2.1. O una función lista que no quieres traer con toda la rama.

13
Pausa

Guardar trabajo con stash

Estás a mitad de algo y necesitas cambiar de rama urgente. git stash aparca tus cambios.

stash
# Guarda los cambios en la "pila"
git stash
git stash push -m "WIP: validación email"

# Ver los stashes guardados
git stash list

# Recuperar el último
git stash pop

# Recuperar uno específico
git stash apply stash@{2}

# Borrar un stash
git stash drop stash@{0}
14
Higiene

Borrar ramas

Después de hacer el merge, la rama no sirve de nada. Bórrala.

borrar ramas
# Borrar local (solo si ya fue mergeada)
git branch -d feature/login

# Forzar borrado (sin importar si se mergeó)
git branch -D feature/experimento

# Borrar en remoto
git push origin --delete feature/login

# Limpiar referencias a ramas remotas que ya no existen
git fetch --prune
Hábito

Al cerrar un PR en GitHub/GitLab hay una opción "Delete branch". Úsala siempre.

15
Flujo

Git Flow

main ─────────────────────────────●─── v2.0 ↑ release ●────────● ↑ develop ─────●──────────────●──────────── ↑ ↑ feature ●──● ●──●──●

main

Solo código en producción. Se toca con releases y hotfixes.

develop

Integración continua. Todas las features llegan aquí.

feature/

Una rama por tarea. Sale de develop, vuelve a develop.

release/

Preparación de versión: solo bugfixes y docs.

16
Alternativa

GitHub Flow

Más simple. Para equipos con despliegue continuo.

main
↓ branch
feature/x
→ PR
Revisión
→ merge
main → Deploy
  • main siempre está desplegable.
  • Cada cambio sale en su propia rama desde main.
  • Abres un PR para revisión y discusión.
  • Cuando el PR se aprueba y el CI pasa, se mergea y se despliega.
¿Cuándo?

Git Flow: releases programadas, muchas versiones vivas. GitHub Flow: deploy continuo, una sola versión en producción.

17
Diagnóstico

Comparar ramas

diff entre ramas
# Qué hay en feature que no está en main
git log main..feature

# Solo los archivos que cambiaron
git diff main..feature --name-only

# El diff completo
git diff main..feature

# Ver qué commits divergieron en ambas
git log main...feature --left-right --oneline
.. vs ...

A..B = commits en B pero no en A. A...B = commits únicos de cada lado (divergencia).

18
Historial limpio

Squash merge

Aplasta todos los commits de la rama en uno solo antes de integrar. El historial de main queda limpio.

feature → main
→git merge --squash
squash
git switch main
git merge --squash feature/login
git commit -m "feat(auth): implementar login con Google"
En GitHub/GitLab

Hay un botón "Squash and merge" en el PR. GitHub Flow + squash merge = historial de main muy legible.

Manos a la obra

Construye este grafo tú mismo

reproducir el grafo
git init notas && cd notas
echo "# Notas" > README.md
git add . && git commit -m "Initial commit"

# feature/abby
git switch -c feature/abby
echo "prefs" > abby.md
git commit -am "added md with preferences"
git switch main && git merge --no-ff feature/abby

# repite con feature/brian, feature/carlos, feature/dana…

# ¡mira tu propio grafo real!
git log --oneline --graph --all --decorate
Pruébalo

Ese último comando imprime el mismo grafo que acabas de ver — en tu propia máquina.
