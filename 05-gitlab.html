Concepto

¿Qué es GitLab?

Una plataforma única para todo el ciclo DevOps: hosting de Git, issues, CI/CD, seguridad y despliegue.

📦

Hosting Git

Repos, como GitHub. Público o privado.

🔀

⚙️

CI/CD

Pipelines definidos en .gitlab-ci.yml, el corazón de GitLab.

Runners

Las máquinas que ejecutan los jobs del pipeline.

04
Recurso central

Merge Requests (MR)

Un MR propone mezclar una rama origen en una rama destino. Corre el pipeline, junta revisiones y mergea.

rama origen
→ MR →
pipeline + revisión
→ merge →
destino (main)
Práctica

Cada MR muestra: el diff, el estado del pipeline, aprobaciones y la opción de squash para un historial limpio.

05
Teoría

CI/CD en teoría

🔄

CI

Integración Continua: mezcla código seguido, corre tests automáticamente en cada push.

🚀

CD

Entrega/Despliegue Continuo: publica a staging/prod automáticamente al pasar.

🎯

Pipeline

Stages → jobs. Los stages corren en orden; los jobs de un stage corren en paralelo.

06
Práctica

Tu primer .gitlab-ci.yml

Un pipeline completo y funcional: instalar deps, lint, test, build.

.gitlab-ci.yml
stages:
  - install
  - test
  - build

cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - node_modules/

install_deps:
  stage: install
  image: node:20
  script:
    - npm ci

lint:
  stage: test
  image: node:20
  script:
    - npm run lint

test:
  stage: test
  image: node:20
  script:
    - npm test
  coverage: '/Lines\s*:\s*(\d+\.\d+)%/'

build:
  stage: build
  image: node:20
  script:
    - npm run build
  artifacts:
    paths:
      - dist/
Cómo corre

Push → GitLab corre install, luego test + lint en paralelo, luego build. dist/ se guarda como artifact para los siguientes.

07
Práctica · deploy

Despliegue con entornos

.gitlab-ci.yml (deploy)
deploy_staging:
  stage: deploy
  image: alpine
  environment:
    name: staging
    url: https://staging.app.com
  script:
    - sh deploy.sh staging
  only:
    - main

deploy_prod:
  stage: deploy
  environment:
    name: production
  script:
    - sh deploy.sh prod
  when: manual      # botón play en el pipeline
  only:
    - tags
Práctica

only: main corre en main. when: manual necesita que un humano pulse play. environment registra cada despliegue en Operations → Environments.

08
Teoría + práctica

Runners

Un runner es la máquina que ejecuta tus jobs. GitLab ofrece runners compartidos; puedes añadir los tuyos.

registrar tu propio runner
# 1. Instala el runner (ej: Linux)
sudo curl -L https://gitlab-runner-downloads.s3.amazonaws.com/latest/binaries/gitlab-runner-linux-amd64 \
  -o /usr/local/bin/gitlab-runner
sudo chmod +x /usr/local/bin/gitlab-runner

# 2. Regístralo (URL + token los da Settings → CI/CD → Runners)
sudo gitlab-runner register

# 3. Arráncalo
sudo gitlab-runner start
Tags

Etiqueta un job (tags: [docker]) para que corra solo en runners con esa etiqueta — ej. un runner con Docker.

09
Práctica

Variables de CI/CD

Guarda tokens y config sin meterlos en el repo. Settings → CI/CD → Variables.

usar una variable
# En .gitlab-ci.yml las variables llegan como entorno
deploy:
  script:
    - curl -H "Authorization: Bearer $DEPLOY_TOKEN" \
           $DEPLOY_URL

# Marca una variable como "masked" para que no salga en los logs
# Marca "protected" para que solo exista en ramas/tags protegidas
Cuidado

Una variable masked debe ser base64-safe y suficientemente larga, o GitLab no la enmascara.

10
Práctica

Container Registry

Cada proyecto GitLab tiene un registry Docker integrado. Construye y sube imágenes en el pipeline.

construir y subir imagen
docker_build:
  image: docker:24
  services:
    - docker:24-dind
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
11
Estrategia

GitLab Flow

main ────────●────────●────────●── \ \ \ pre-prod ●────────●────────●── \ \ \ prod ●────────●────────●──

main es la fuente de verdad. Cada entorno (pre-prod, prod) es una rama que hace cherry-pick/merge desde main. Desplegar = mergear a esa rama.

Práctica

Merge main → pre-prod lo prueba; merge pre-prod → prod lo publica. Cada entorno es observable y reversible.

CLI · configurar

glab — autenticar

login
# Login interactivo (abre el navegador o pide token)
glab auth login
#  → elige gitlab.com o self-hosted → pega tu token

# Crea el token en: User Settings → Access Tokens
#  scope: api, read_repository, write_repository

# Comprueba el estado
glab auth status

# Para self-hosted, indica la instancia
glab auth login --hostname gitlab.miempresa.com
15
CLI · MRs

glab — Merge Requests

mr
# Crear MR
glab mr create --title "feat: login" \
  --description "Añade login con Google" --target-branch main

# Listar MRs abiertos
glab mr list

# Ver el MR actual en el navegador
glab mr view --web

# Bajar el MR !42 a tu local
glab mr checkout 42

# Aprobar y mergear
glab mr approve 42
glab mr merge 42 --squash --remove-source-branch

18
Flujo completo

Un flujo de MR completo sin salir del terminal

el ciclo entero
# 1. Rama
git switch -c feature/login

# 2. Trabaja y confirma
git commit -am "feat(auth): login"

# 3. Sube y abre el MR
git push -u origin feature/login
glab mr create --fill --target-branch main

# 4. Mira el pipeline
glab ci status

# 5. Mergear y limpiar
glab mr merge --squash --remove-source-branch

Trampas

Errores comunes

🔓

main sin proteger

Cualquiera puede push a main. Protégela: Settings → Repository → Protected branches.

🔑

Token en el repo

Usa variables de CI/CD, nunca hardcodees secretos en .gitlab-ci.yml.

🐌

Sin cache

Cada job reinstala deps. Añade un cache: key + paths: node_modules/.

Ahora Git avanzado

Rebase interactivo, reflog, bisect, hooks, submodules y worktrees.
